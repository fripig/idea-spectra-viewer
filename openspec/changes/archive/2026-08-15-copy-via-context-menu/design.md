## Context

工具視窗的樹已經支援 IDE 標準的 Copy：SpectraChangesPanel 實作 UiDataProvider，在資料快照中提供 PlatformDataKeys.COPY_PROVIDER，而它的可用性判斷與實際複製都轉呼叫 ChangeTreeNodes.kt 裡的純函式 copyTextFor。複製的規則因此已經有單元測試覆蓋，不需要在這個變更裡重寫。

樹目前沒有安裝任何 popup action group，右鍵按下去沒有任何反應。唯一的滑鼠互動是雙擊 artifact 節點開檔，作法是自行攔截 DoubleClickListener 後做座標命中測試。

建置設定刻意不引入 IntelliJ 平台測試框架，因此 UI 接線本身沒有自動化測試覆蓋，驗證要靠手動操作。

## Goals / Non-Goals

**Goals:**

- 滑鼠使用者在樹上按右鍵就能看到複製入口，不必先知道有 Copy 快捷鍵。
- 右鍵複製與快捷鍵複製產出完全相同的文字，且停用時機一致。
- 不因為多一個入口而多一份複製規則。

**Non-Goals:**

- 選單不放第二個項目。複製 artifact 路徑、在檔案總管中顯示、刪除 change 都不在這次範圍。
- 不改變樹的繪製結果，也不新增節點上的可點擊圖示。
- 不改動 copyTextFor 的行為，也不新增複製規則的單元測試。
- 不動掃描層，右鍵與複製都不觸發重新掃描。

## Decisions

### 選單項目自訂文字但共用同一個啟用判斷

選單裡放的是一個文字為「Copy Change Name」的自訂 action，而不是平台通用的 Copy。通用的 Copy 在選單裡只說「複製」，沒說複製的是什麼；這個樹上有三種節點，其中兩種不可複製，選單文字明講對象能省掉使用者的一次嘗試。

代價本來會是「啟用判斷寫成兩份」，但這裡避開了：自訂 action 的 update 與 CopyProvider 的 isCopyEnabled 呼叫同一個面板方法，而那個方法又只轉呼叫既有的純函式，所以「什麼算可複製」全程只有一個答案。action 執行複製時也直接轉呼叫面板既有的 CopyProvider，不自己碰剪貼簿。

快捷鍵顯示沿用平台 Copy action 的 shortcut set，於是選單項目右側仍會顯示使用者自己設定的複製快捷鍵，兩個入口在視覺上是同一件事。

### 以平台的 popup 安裝機制掛上選單

用平台提供的 popup 安裝方式把 action group 掛在樹上，不自行攔截滑鼠事件、不自行判斷 popup trigger。平台的安裝點已經處理了各作業系統觸發 popup 的按鍵差異（macOS 的 Control 加點擊、Windows 與 Linux 的右鍵放開），自行攔截等於重寫一次這些平台差異。

action group 以程式建立並直接掛在樹上，不在 plugin.xml 宣告。這個選單只服務這一個元件，宣告在 plugin.xml 會讓它變成全域可見的 action，對其他人沒有意義。

### 右鍵先確定選取再開選單

在沒有被選取的節點上按右鍵時，該節點要先成為選取，選單才顯示。否則選單動作會套用在畫面上別處的舊選取，使用者以為複製的是手指所指的那個 change。

右鍵落在已經被選取的多列之中時，選取範圍保持不變，讓「多選後右鍵複製」能如預期運作。右鍵落在空白處時，選取範圍不變，選單仍會顯示，項目是否可用由既有判斷決定。

平台的樹元件可能已經自帶這個行為，實作時先確認實際行為，只有在確認缺少時才補上，避免多寫一份與平台重複、日後行為分岔的選取邏輯。

**確認結果（平台已自帶）**：在沙箱 IDE 中先選取一個 change，再到另一個未選取的 change 上按右鍵，選取框跟著移到右鍵所指的節點。因此這個變更不寫任何選取程式碼；補一份只會是與平台重複的第二來源，日後平台調整行為時反而會分岔。

## Implementation Contract

**Behavior**：使用者在 Spectra 工具視窗的樹上按右鍵，出現一個只有「Copy Change Name」一項的選單，項目右側顯示使用者目前的複製快捷鍵。選取範圍含至少一個 change 節點時該項目可用，點下去把這些 change 的名稱寫入剪貼簿，多個名稱以換行分隔並保持樹上由上而下的順序；不含 change 節點時該項目停用，剪貼簿不變。右鍵落在未被選取的節點上時，該節點先成為唯一選取，選單再出現，於是複製到的是使用者指到的那個 change。複製成功後沒有任何通知。

**Interface**：

- SpectraChangesPanel 在初始化時建立一個只含「Copy Change Name」這一項的 action group，並用平台的 popup 安裝方式掛在樹上。該項目的啟用判斷與實際複製都轉呼叫面板既有的複製路徑，快捷鍵顯示沿用平台 Copy action 的 shortcut set。
- 複製文字仍然只由既有的純函式決定，這個變更不新增也不修改任何計算複製文字的程式碼。
- 面板既有的 COPY_PROVIDER 提供方式維持不變；選單與快捷鍵共用同一個 provider。

**Failure modes**：選取範圍沒有可複製對象時，選單項目呈現停用而不是按下去沒反應，也不寫入空字串到剪貼簿。右鍵發生在樹的空白處時不拋出例外，選單照常顯示。

**Acceptance criteria**：

- 執行專案既有的建置與測試指令後全部通過，且測試數量與內容不變（這次不新增單元測試）。
- 手動驗證：在單一 change 節點上右鍵複製，貼出來的字串與樹上顯示的名稱相同且不含進度數字；在分組節點與 artifact 節點上右鍵，Copy 項目呈現停用；多選兩個 change 後右鍵複製，得到兩行且順序與樹上一致；在未選取的 change 節點上直接右鍵複製，得到的是該節點的名稱而不是先前選取的那個。
- 手動驗證：右鍵與複製都不觸發重新掃描，樹的展開狀態、排序與篩選文字維持不變。

**Scope boundaries**：

- In scope：SpectraChangesPanel 建立 action group 並安裝 popup、必要時補上右鍵選取行為、changes-tool-window 規格既有需求的擴充。
- Out of scope：copyTextFor 與其測試、繪製器、工具列、掃描層、plugin.xml、選單的其他項目。

## Risks / Trade-offs

- 選單項目是自訂 action，多了一層接線，日後有人只改 CopyProvider 就可能讓兩個入口分岔 → 自訂 action 不自己判斷也不自己碰剪貼簿，兩件事都轉呼叫面板既有的複製路徑，要分岔得先刻意繞開它。
- 選單文字與 IDE 其他地方的通用 Copy 不同 → 兩者顯示同一個快捷鍵，而且選單只有一項，不會出現「該按哪個」的猶豫。
- 接線只能手動驗證，沒有自動化測試 → 這個變更刻意不搬動任何有測試覆蓋的邏輯，能出錯的範圍限縮在「選單有沒有出現、右鍵有沒有先選取」這兩件肉眼可見的事。
- 若平台的樹元件本來就會在右鍵時調整選取，補寫一份會造成兩份行為 → 實作時先確認再決定是否補，並把確認結果寫進任務的驗證。
