## Context

Spectra Viewer 的第一版把排序寫死在掃描層：`ChangeScanner` 的分組掃描結尾以名稱遞增排序，並在 `change-discovery` spec 立下「Within each group, changes SHALL be sorted by name」這條要求。同一版還做了另一個決定——完全不讀 `.openspec.yaml`，理由記在 `ChangeScanner` 的 `readChange` 註解：不讀就不可能因為 metadata 壞掉而讓 change 消失。

這兩個決定現在都擋路。建立日期唯一的來源就是 `.openspec.yaml` 的 `created` 欄位；而使用者可切換的排序若留在掃描層，每換一次排序就要重掃磁碟。

已在本機以 spectra 2.3.1 實測 CLI 的排序行為，作為對齊基準：`spectra list --sort modified`（預設）為新到舊，`--sort name` 為 A 到 Z。

`.openspec.yaml` 的實際內容範例：

    schema: spec-driven
    created: 2026-08-13
    created_by: fripig <fripig@gmail.com>

建立日期只到日，沒有時間。

## Goals / Non-Goals

**Goals:**

- 分組內排序可由使用者切換，切換不觸發磁碟重掃
- 名稱篩選即時反應，且讓使用者一眼看出「資料被篩掉」而非「資料不見了」
- 推翻不讀 `.openspec.yaml` 的決定時，保留它原本要守護的性質：壞掉的 metadata 不得讓 change 從清單消失
- 與 Spectra CLI 的排序語意一致，讓終端機與 IDE 呈現同一個心智模型

**Non-Goals:**

- 不做跨分組排序、不做狀態篩選、不做分組開關
- 不持久化排序與篩選狀態
- 不做正規表示式或模糊比對
- 不解析 `.openspec.yaml` 的 `created` 以外欄位

## Decisions

### 建立日期以寬容解析取自 .openspec.yaml，推翻既有的不讀決策

掃描層改為讀取每個 change 目錄下的 `.openspec.yaml`，只取 `created` 一個欄位。

原決策真正要守的是「壞掉的 metadata 不能讓 change 消失」，而「完全不讀」只是當時達成該性質最省事的手段。改為寬容解析後該性質仍然成立：檔案缺失、無法讀取、欄位不存在、日期格式不合，一律讓建立日期為未知，change 照常列出。

既有 spec 已有一條 `Degrade gracefully on unreadable changes`，其中明訂 `.openspec.yaml` 缺失或無法解析時該 change 仍須列出。該條在第一版形同虛設，本次改動讓它開始有實質約束力，因此不需新增要求，只需讓實作真正滿足它。

替代方案：以檔案系統的建立時間作為建立日期。已評估後放棄，該時間在複製、搬移、git checkout 後都會改變，且 parked change 曾被搬移過，數值不可信。

### 修改日期取所有 Markdown 檔案的最新修改時間

修改日期定義為 change 目錄下所有 Markdown 檔案修改時間的最大值。沒有任何 Markdown 檔案時為未知。

不用 change 目錄本身的修改時間：目錄的修改時間只在新增或刪除項目時變動，編輯既有檔案內容不會更新它。使用者持續編輯 `tasks.md` 時，以目錄時間排序會看起來凍結，而且這種失真很隱晦、不容易察覺。

成本可忽略：掃描層本來就已走訪全部 Markdown 檔案以建立 artifact 清單，取修改時間只是每個檔案多一次屬性讀取。

### 排序責任由掃描層移交呈現層

`ChangeScanner` 不再對分組內的 change 排序，快照內的順序視為未定義。排序改由呈現層在建立樹狀模型前套用。

理由：快照只該承載資料，順序是呈現的事。留在掃描層的話，切換排序等同要求重掃磁碟——對使用者是無謂的延遲，對程式是把兩個不相干的關切綁在一起。

此決定使 `change-discovery` 的 `Scan changes from all three Spectra sources` 成為 MODIFIED 要求，需移除其中的排序句與對應情境。

### 排序方向與次要鍵對齊 Spectra CLI

三種排序的方向：Name 為名稱遞增；Modified 與 Created 皆為新到舊。次要鍵一律為名稱遞增，因為建立日期只到日，同日建立的 change 會大量並列，沒有次要鍵時順序不穩定。

預設值為 Modified，與 CLI 的預設一致。

### 日期未知的 change 一律排在最後

以日期排序時，日期未知的 change 永遠排在該分組最末，與排序方向無關。

理由：未知不等於很舊。若把未知當成極小值，一個沒有 `.openspec.yaml` 的 change 會在「最舊」排序下浮到頂端，讀起來像是斷言了它很舊。沉底則明確表達「這筆沒有可比的資訊」。

### 篩選只比對名稱，計數改為符合數與總數

篩選以不分大小寫的子字串比對 change 名稱，同時套用於三個分組。命中的 change 其底下 artifact 節點全部顯示，artifact 路徑本身不參與比對。

分組節點在篩選字串非空時顯示符合數與總數兩個數字，字串為空時維持單一數字。理由：只顯示符合數的話，使用者看到 Archived 從 20 掉到 0 會以為資料掉了；並列總數才讀得出「是被篩掉的」。

分組節點在零筆符合時仍然顯示，沿用既有要求。

### 不引入 YAML 函式庫，以單行掃描取單一欄位

`created` 欄位的解析以逐行掃描完成：找出第一個以 `created:` 開頭的頂層行，取其值並嘗試以 ISO 日期格式解析。

理由：只需要一個純量欄位，引入 YAML 函式庫是為了一行值背負一整個相依與其攻擊面。逐行掃描的限制是不支援巢狀或多文件 YAML——而 Spectra 產生的 `.openspec.yaml` 是扁平的鍵值對，不觸及這些限制。任何不合預期的內容都落入「未知」這條既有路徑，不會造成錯誤。

## Implementation Contract

### 使用者可觀察的行為

- Tool Window 工具列新增一個排序動作，提供 Name、Modified、Created 三個互斥選項，當前選項有勾選標記。切換後樹狀立即依新順序重建，且不重新掃描磁碟。
- 工具列新增一個文字輸入欄位，輸入即時篩選。輸入非空時，只有名稱包含該子字串（不分大小寫）的 change 節點顯示。
- 分組節點文字：篩選字串為空時顯示分組名稱與單一總數；非空時顯示符合數與總數兩個數字。
- Refresh 後，當前的排序與篩選設定保持不變並套用於新快照。
- 關閉並重開 IDE 後，排序回到 Modified，篩選字串為空。

### 資料契約

掃描層對每個 change 額外報告兩個欄位：

- 建立日期：由 `.openspec.yaml` 的 `created` 欄位解析而得的日期，或未知
- 修改日期：change 目錄下所有 Markdown 檔案修改時間的最大值，或未知（無 Markdown 檔案時）

快照內各分組的 change 順序不再有保證，呼叫端不得依賴。

排序與篩選以純函式表達，輸入為一份快照加上排序選項與篩選字串，輸出為套用後的分組資料。函式不接觸檔案系統，因此可在事件派發執行緒上呼叫。

### 排序規則

- Name：名稱遞增
- Modified：修改日期新到舊，日期未知者置於最末，同日期以名稱遞增
- Created：建立日期新到舊，日期未知者置於最末，同日期以名稱遞增

### 失敗模式

- `.openspec.yaml` 缺失、無法讀取、無 `created` 欄位、或該欄位的值無法解析為日期：建立日期為未知，change 照常列出，不寫警告也不彈出對話框
- 讀取某個 Markdown 檔案的修改時間失敗：該檔案不參與最大值計算，其餘檔案照常；全部失敗則修改日期為未知
- 篩選字串使得三個分組皆為零筆：三個分組節點仍然顯示，各自的符合數為零

### 驗收條件

- 掃描層測試涵蓋：`created` 正常解析、檔案缺失、欄位缺失、日期格式非法四種情形皆不使 change 消失；修改日期在編輯既有 Markdown 檔案後會前進，而在僅讀取時不變
- 排序純函式測試以設計中列出的三筆資料為輸入，逐一斷言三種排序的完整輸出順序，含日期未知者沉底
- 篩選純函式測試斷言不分大小寫比對、三分組同時套用、以及零符合時分組仍存在
- 沙箱 IDE 手動驗證：切換三種排序後順序改變且無磁碟重掃；輸入篩選字串後分組計數變為兩個數字；Refresh 後排序與篩選維持
- 以 Gradle wrapper 執行 test 任務全數通過

### 範圍邊界

在範圍內：模型新增兩個日期欄位與排序選項型別、`.openspec.yaml` 的 `created` 解析、修改日期蒐集、掃描層移除排序、排序與篩選純函式、工具列的排序動作與篩選輸入欄位、分組計數呈現、對應單元測試。

在範圍外：跨分組排序、狀態篩選、分組開關、狀態持久化、正規表示式或模糊比對、`.openspec.yaml` 其他欄位、篩選 artifact 節點、排序 artifact 節點。

## Risks / Trade-offs

- 使用者已習慣第一版的名稱排序，預設改為修改時間會讓順序看起來變了 → 排序選項顯示當前選擇，且 Name 選項一直可用；與 CLI 預設一致的價值大於維持舊預設
- 建立日期只到日，Created 排序在單日內完全無鑑別度 → 以名稱作次要鍵確保順序穩定；需要精確時序時 Modified 排序本來就更準確
- 逐行解析取代 YAML 函式庫，若 Spectra 未來把 `.openspec.yaml` 改成巢狀結構會解析失敗 → 解析失敗落入既有的「未知」路徑，只損失建立日期而不影響其他功能；屆時再評估是否引入函式庫
- 篩選在大量 archived change 時每次按鍵都重建整棵樹 → 篩選是記憶體內的字串比對，數十至數百筆的規模下成本遠低於一次重繪；若日後成為問題再引入輸入去抖動
