## Context

Spectra Changes tool window 目前的檢視狀態由三個部分組成：snapshot（掃描結果，存於 panel 的 `lastSnapshot`）、排序（`ChangeOrder`）、名稱過濾（一個 `String`）。`applyView` 是純函式，把 snapshot 加上排序與過濾轉成 `GroupView` 清單，因此改變排序或過濾只需重建樹，不必重新掃描磁碟。

提案者名稱來自 `.openspec.yaml` 的 `created_by` 欄位，由 `ChangeMetadataParser` 剝除 email 後存為 `SpectraChange.createdBy`，型別為 `String?`，`null` 代表未知。這個值已經顯示在 change 節點的灰字區段（`changeNodeDetails`）。

既有規格明文要求提案者不參與名稱過濾，並有測試 `the filter does not match the proposer` 守著這個行為。因此作者過濾必須是一個獨立的維度，不能靠擴充名稱過濾的比對範圍達成。

群組節點的計數由 `groupCountText` 依 `GroupNode.filtering` 決定顯示 `total` 或 `matched/total`，而 `filtering` 目前直接等於「名稱過濾字串非空」。

本專案目前沒有任何持久化機制，排序與名稱過濾都只是 panel 的欄位，工具視窗重建即回到預設。

## Goals / Non-Goals

**Goals:**

- 讓使用者能以提案者為條件篩選 change，且可同時選取多位提案者。
- 讓「未標示提案者」本身成為一個可篩選的條件，而不是一個撈不出來的黑洞。
- 把「目前是否正在過濾」收斂成單一判斷來源，讓群組計數在任一種過濾生效時都誠實顯示 `matched/total`。
- 維持既有架構特性：過濾邏輯是純函式、可在無 IDE fixture 的情況下測試、改變過濾不觸發磁碟掃描。

**Non-Goals:**

- 不從 git commit author、`proposal.md` 署名或任何 `created_by` 以外的來源推導作者。過濾條件必須與畫面上看得見的字串一致。
- 不做過濾條件的持久化，不引入 `PropertiesComponent` 或 `PersistentStateComponent`。
- 不在名稱過濾輸入框引入查詢語法（如 `author:alice` 前綴）。
- 不改變名稱過濾既有的比對規則、不讓提案者被名稱過濾比對。
- 不改動掃描層（`ChangeScanner`、`ChangeMetadataParser`）與 `SpectraChange` 的資料形狀。
- 不改變 change 節點上提案者的顯示方式。

## Decisions

### 以獨立的複選 popup 呈現作者過濾，而非擴充名稱輸入框

作者是低基數的列舉值，使用者需要的是「從既有的人選中挑」而非「輸入字串比對」。讓名稱輸入框同時比對作者（OR）會使結果不可預測：輸入 `fri` 可能因為作者名命中而帶出一批名稱不相干的 change，而群組列的 `matched/total` 無法說明是哪一邊命中。加入 `author:` 前綴語法則是在一個完全沒有語法概念的輸入框引入查詢 DSL，成本與收益不成比例。

作者過濾與名稱過濾為 AND 關係：兩者都生效時，change 必須同時符合名稱與作者條件。

**替代方案**：單選下拉。已排除——「Alice 和 Bob 兩人手上的提案」是真實需求，單選逼使用者切換兩次並自行在腦中合併；而在 `ToggleAction` 模式下，複選的實作成本幾乎等同單選。

### 使用 toolbar 的 popup action group 而非 Swing 下拉元件

沿用既有 `SortAction` 的模式：一個 `DefaultActionGroup` 掛在 toolbar 上，內含每位作者一個 `ToggleAction`。理由有三：一是這是 IntelliJ 工具視窗的既有慣例，使用者不需學習新互動；二是工具視窗通常很窄，名稱輸入框已佔用版面中央，再並排一個下拉元件會把輸入框壓到不堪使用；三是 `ToggleAction` 讓「目前勾選了誰」由 `isSelected` 自行回報，不必手動同步元件的 model 與選取狀態——後者在作者清單隨 Refresh 變動時特別容易產生不一致。

按鈕文字為 `Filter by Author`，未知作者項目文字為 `Unknown`，沿用既有規格中描述提案者未知情形所用的字彙，不另創同義詞。

### 以具名布林表達未知作者，而非集合中的 null 元素

過濾條件的資料形狀為「作者名稱集合」加上「是否納入未知作者」兩個欄位，而不是一個可含 `null` 元素的集合。可空元素的集合在 `contains` 判斷上極易出錯，且讀者無法從型別看出 `null` 是有意義的成員還是遺漏。具名布林讓「未知」成為設計中的一等概念。

`Unknown` 在候選清單中固定排在最後，不依字母序混入人名之間——它不是一個人名，排在字母序中間會被讀成有位提案者叫做 Unknown。這與既有排序邏輯「日期未知者永遠排最後、不搶第一」的原則一致。

### 過濾條件收斂為單一值物件，取代分散的 String 參數

將名稱過濾與作者過濾合併為一個過濾條件值物件，`applyView` 與過濾函式改為接受它。此物件自行回答「是否正在過濾」與「某個 change 是否命中」兩個問題。

若改為保留既有的名稱過濾函式、另外並排一個作者過濾函式，等於把「過濾」這個單一概念切成兩半，之後每個呼叫端都得自行記得兩者都要呼叫、以什麼順序呼叫——這正是既有註解在防範的那類漏洞。收斂之後，「有沒有在過濾」與「有沒有命中」各只有一個答案，群組計數的 `filtering` 旗標也直接取自此物件。

這一步是純機械重構：既有測試改變呼叫簽章，但斷言與語意完全不動，重構完成時測試應全數維持通過。

### 候選作者清單取自完整 snapshot，並在 Refresh 後與選取取交集

候選清單由 Active、Parked、Archived 三個群組聯集算出。過濾本身就同時作用於三個群組，若清單只取自 Active，一個僅出現在 Archived 的作者將永遠無法被選取——但他的 change 就顯示在畫面上，選不到看得見的東西是明顯的缺陷。清單也不隨群組展開狀態變動，否則項目會在展開與收合之間跳動。

Refresh 後，選取的作者與新 snapshot 的候選取交集：仍存在者維持勾選，已消失者自動解除。若改為靜默保留已消失的勾選，使用者會面對一棵全空的樹，而唯一的成因是一個已從 UI 上消失、因而無從取消的勾選——這是死鎖。若改為在清單中保留「幽靈作者」項目，則需維護一份只會越來越髒的歷史清單。

候選項目少於兩項時停用該按鈕：打開一個空的或只有單一選項的選單無法提供任何有效操作，而選單中僅有 `Unknown` 一項時勾選它等同於不過濾。停用（而非隱藏）能明確傳達「功能存在，但此專案沒有可用資料」，也避免 toolbar 的按鈕數量隨專案內容變動。

### 將快照到過濾條件的調和抽成純函式，讓接線層只剩指派

掃描完成後要做三件有順序的事：由新 snapshot 算出候選清單、拿新候選清單調和既有選取、再把兩者放回面板狀態。前兩件事若寫在面板的掃描回呼裡，就只能靠啟動沙箱、手動搬走一個 change、按下 Refresh 來驗證——一個沒有人會例行執行的步驟，於是這段順序邏輯實際上不受任何東西守護。

把「snapshot 加上目前的過濾條件，得出新的候選清單與調和後的過濾條件」抽成一個回傳兩者的純函式後，接線層剩下的只有兩個欄位指派。順序錯誤（例如拿舊的候選清單去調和、或先指派再調和）在純函式裡是可測的，在回呼裡則不是。

替代方案：維持手動驗證。已排除——這段邏輯存在的唯一理由，就是避免使用者在 Refresh 後看到一棵無法解釋的空樹；讓它成為整個變更裡唯一沒有測試涵蓋的判斷，與它的重要性完全相反。

### 不在候選項目上顯示 change 筆數

在 `Unknown` 或作者名稱旁附加數字會產生無法定義的語意：該數字是該作者的總數、是符合當前名稱過濾後的數量、還是在其他已勾選作者之下的增量？三種解讀都有人期待，擇一都會誤導其餘使用者。而使用者真正需要的數字，在勾選後由群組列的 `matched/total` 直接提供。

## Implementation Contract

**Behavior**

- 工具視窗 toolbar 在既有的 Refresh 與排序按鈕之外，出現一個作者過濾按鈕。點擊展開一份候選作者清單，每項可獨立勾選、可同時勾選多項。
- 未勾選任何項目時，作者過濾不生效，所有 change 依名稱過濾結果顯示。
- 勾選一項或多項時，只有提案者屬於已勾選集合的 change 會顯示；勾選 `Unknown` 時，`createdBy` 為 `null` 的 change 會顯示。多項勾選之間為 OR。
- 名稱過濾同時非空時，change 必須同時符合名稱與作者條件（AND）才顯示。
- 候選清單依作者名稱字母序排列，比較時不分大小寫；`Unknown` 一項恆在清單末端，且僅在 snapshot 中確實存在 `createdBy` 為 `null` 的 change 時出現。
- 候選項目總數少於兩項時，按鈕呈現停用狀態且無法展開。
- 作者過濾生效（已勾選任一項）時，群組節點顯示 `matched/total`；與名稱過濾是否非空無關。
- 改變勾選只從記憶體中的 snapshot 重建樹，不觸發檔案系統掃描。
- Refresh 後，仍存在於新 snapshot 候選清單中的勾選予以保留，不存在者自動解除；名稱過濾文字的保留行為維持不變。
- 工具視窗重新建立後，作者過濾回到未勾選狀態。

**Interface / data shape**

- 新增一個過濾條件值物件，持有三項資料：名稱過濾字串、已勾選的作者名稱集合、是否納入未知作者的布林值。它對外提供兩個查詢：此條件是否正在過濾（供群組計數判斷），以及某個 change 是否命中。空字串加空集合加布林為否，代表完全不過濾。
- 新增一個純函式，由 snapshot 算出候選作者清單：三群組聯集、去重、依字母序（不分大小寫）排列，並回報 snapshot 中是否存在未知作者。此函式不存取檔案系統。
- 既有的過濾函式與檢視組裝函式改為接受上述值物件，取代原本的名稱字串參數。群組計數所依據的 `filtering` 旗標改由該值物件回答。
- 提案者顯示、複製到剪貼簿的內容、排序邏輯、`SpectraChange` 的欄位皆不變。

**Failure modes**

- `createdBy` 為 `null` 一律視為「未知作者」，不視為錯誤、不記錄警告，也不以佔位字串填補。
- snapshot 為空或非 Spectra 專案時，候選清單為空、按鈕停用，不拋出例外。
- 已勾選的作者在新 snapshot 中不存在時，該勾選靜默解除，不發出通知——使用者觀察到的是清單中該項目消失，此為預期行為。

**Acceptance criteria**

- 新增的過濾條件值物件、候選清單函式、以及快照到過濾條件的調和函式皆有 JUnit 測試涵蓋，測試不依賴 IDE fixture，可由 Gradle test 任務直接執行。
- 涵蓋的案例至少包含：僅名稱過濾、僅作者過濾、兩者同時生效、勾選未知作者、多位作者的 OR 行為、候選清單的字母序與 `Unknown` 殿後、snapshot 無未知作者時 `Unknown` 不出現、Refresh 後選取取交集、候選少於兩項時的停用判斷。
- 既有測試 `the filter does not match the proposer` 維持存在且通過，斷言內容不變（僅隨簽章重構調整呼叫方式）。
- 既有的群組計數測試在重構後全數通過，並新增「僅作者過濾生效時顯示 matched/total」的案例。
- 掃描完成後的調和以單元測試驗證：同一個 snapshot 與過濾條件輸入，回傳的候選清單與調和後的過濾條件符合預期，涵蓋「作者仍在」「作者已消失」「未知作者候選已消失」三種情況。
- 需要人眼確認的僅剩版面外觀：按鈕位置、popup 可複選、名稱輸入框未被壓縮。過濾與調和的正確性一律由測試回答。
- Gradle build 通過，包含既有的 plugin 驗證任務。

**Scope boundaries**

- 在範圍內：過濾條件值物件、候選清單函式、快照到過濾條件的調和函式、既有過濾與檢視組裝函式的簽章重構、群組計數旗標的語意調整、toolbar 的 action group 與勾選狀態接線、規格文件更新。
- 不在範圍內：掃描層與中繼資料解析、`SpectraChange` 的欄位、提案者的渲染方式、名稱過濾的比對規則、排序邏輯、複製行為、送出終端機指令的行為、任何持久化機制。

## Risks / Trade-offs

- **不持久化，使用者每次開啟工具視窗都要重新勾選** → 這是刻意的取捨。被記住的過濾條件是隱形的：下次開啟 IDE 看到少了一半的 change，唯一線索是 toolbar 上一個外觀無異狀的按鈕，這是最典型的誤報 bug 情境。與既有的排序、名稱過濾行為保持一致，也避免為單一功能引入本專案第一個持久化機制。
- **Refresh 後自動解除已消失作者的勾選，可能讓使用者以為系統擅自改動了設定** → 以「候選清單中該項目同時消失」作為視覺線索緩解；相較於留下一個無法取消的隱形過濾條件導致空樹，此行為的困惑程度低得多。
- **候選清單由 snapshot 動態算出，作者眾多的專案清單可能很長** → 就本專案的實際使用情境（單一 repo 的提案者），清單長度可控。若日後出現數十位提案者，再考慮加入搜尋或分頁，屬於後續變更範疇。
- **重構既有過濾函式簽章會擴散到多個測試檔案** → 刻意將其獨立為第一個任務，且該任務不改變任何斷言語意，確保重構造成的失敗與新功能造成的失敗不會混在一起，出問題時容易定位。
- **UI 接線層不寫測試** → 與既有作法一致：panel 本身沒有測試，邏輯一律推到純函式層。此變更把所有判斷（命中、清單、交集、停用條件、掃描後的調和順序）都留在純函式中，接線層只剩欄位指派與轉呼叫。殘留風險限於版面外觀與 action 註冊，兩者在沙箱中一眼可見，不會靜默出錯。
