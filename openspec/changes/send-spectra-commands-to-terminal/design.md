## Context

Spectra Viewer 目前是一個唯讀的樹狀檢視：掃描檔案、畫出三個群組、雙擊開啟 Markdown、右鍵複製 change 名稱。它從未寫入任何東西，也只相依 `com.intellij.modules.platform` 一個模組。

這次要新增的行為第一次跨出這個邊界：把文字送進另一個 plugin（bundled terminal）擁有的 UI。這帶來三個既有程式碼沒處理過的問題——目標 plugin 可能被停用、目標 widget 可能還沒連上 shell、以及送出的文字會落在使用者正在工作的環境裡。

既有的三個約束必須維持：

- 掃描以外的操作都不碰檔案系統。複製 change 名稱刻意做成純記憶體操作，送指令也應如此。
- 測試不依賴 IDE fixture。建置腳本刻意不引入平台測試框架，因為它會註冊自己的 JUnit 5 listener，在真實 IDE 測試環境外無法實例化。
- 判斷「動作是否可用」與「動作實際做什麼」必須出自同一份邏輯。既有的 copy provider 已經遵守這點，避免出現按了沒反應的選單項。

## Goals / Non-Goals

**Goals:**

- 讓使用者從樹上的一個 change 直達「Claude 開始處理它」，中間不必手工組裝指令字串。
- 讓選單在被點下去之前就說清楚接下來會發生什麼，不靠事後通知補救。
- 把對 terminal plugin 的相依收斂成一個可以整檔刪除的接縫，刪掉之後剪貼簿那條路仍然完整可用。
- 指令文字的組法保持純函式，沿用既有的無 IDE fixture 測試方式。

**Non-Goals:**

- 不自動按 Enter。plugin 無從驗證使用者切對了 tab，最後一道確認留給使用者。
- 不自動開新 terminal tab，也不自動啟動新的 Claude session。
- 不偵測哪個 tab 裡跑著 Claude。
- 不做指令清單設定頁，四個指令寫死。
- 不依群組過濾指令，三個群組的子選單內容一致。
- 不改動既有的 Copy Change Name 行為。

## Decisions

### 指令文字由純函式產生，與既有的複製邏輯並列

指令字串的組法是「拿一個 change 節點和一個指令種類，產出一行文字」，沒有任何 IDE 依賴。它放在樹節點模組裡，緊鄰既有的複製文字函式，因此可以用現有的純 JVM 測試覆蓋，不必引入平台測試框架。

替代方案是讓送出端自己拼字串。否決的理由是：那樣一來「選單上顯示的文字」與「實際送出的文字」會由兩段程式各自產生，兩者遲早會不一致，而這正是使用者最不能容忍出錯的地方——他看到的和送出去的必須是同一串字。

四個指令以一個列舉表示，每個成員帶自己的 slash 指令名稱。新增指令的成本是加一個列舉成員。

### terminal 相依收斂成單一 adapter，且可整檔刪除

只有一個檔案 import `org.jetbrains.plugins.terminal` 與 `com.intellij.terminal.ui` 底下的型別。它對外只暴露兩件事：目前是否有可送出的目標，以及把一段文字送過去。面板層不認識任何 terminal 型別。

不再多包一層抽象介面。中間再加一個「送出目標」介面只會是純轉發，沒有藏住任何行為，也沒有第二種實作需要替換。

刪除測試：把這個檔案刪掉，剪貼簿那條路完全不受影響，只是子選單永遠顯示 Copy Command。這正是 terminal plugin 被停用時的行為，所以降級路徑不是特例，而是這個接縫天生的預設狀態。

這個接縫同時承擔兩個終端機引擎。IDE 兩者都出貨且使用者可以切換，而它們的分頁互不相認：改版引擎的分頁對舊版管理器是隱形的。接縫內部先問改版引擎、再退回舊版，任何一邊都取不到就等於沒有目標。把單一引擎當成全世界，正是這個順序存在的理由。

### 只填入不執行，並把焦點交給 terminal

送出交給改版終端機（reworked，2025.2 起的預設引擎）的送文字建構器，它以「是否要執行」為一個明確開關：呼叫 `shouldExecute()` 才會執行，因此不呼叫它就是這條規則的保證，而不是靠我們自己控制有沒有附上換行字元。

建構器也處理 bracketed paste mode，這比裸寫 tty 位元組重要：一個正在讀取提示字元的程式——例如跑著的 Claude 工作階段——需要分辨這段文字是貼上的還是逐鍵敲入的。

**實測修正**：初版走的是 `TerminalWidget` 的 tty 連線，在改版終端機下整段不成立——`TerminalToolWindowManager` 認不得它的分頁，`findWidgetByContent` 回傳 null 且 widget 清單為空。介面方法確實存在於平台層，但**取不到改版終端機的 widget 實例**。因此送出改以改版終端機自己的分頁管理器為主要路徑，舊版（classic）引擎的 tty 寫入退為保底，因為使用者仍可把終端機切回舊引擎。

因為使用者還要自己按 Enter，送出後必須啟動 Terminal 工具視窗並把焦點交給目標 widget——否則使用者按下的 Enter 會落在樹上，什麼也不會發生，看起來就像指令沒送出去。焦點轉移是這個決策的必要配套，不是附加的體貼。

替代方案是自動執行。否決的理由在提案的 Non-Goals 已記錄：代價不對稱。填入錯誤的 tab 只是多一行未送出的文字，自動執行則可能被一個正在等待輸入的互動程式當成回答吃掉。

### 選單標題隨可送出狀態切換

子選單標題在動作更新時計算：有可送出的目標時顯示 Send to Terminal，沒有時顯示 Copy Command。子項目文字始終是完整指令，兩種狀態下都一樣。

替代方案是固定標題加上事後通知。否決的理由是：既有規格明訂複製成功不產生任何可見回饋，為了降級而破例會讓同一個功能有時安靜有時吵。讓標題先說實話，就不需要事後解釋，也維持了規格的一致性。

### terminal plugin 缺席時的載入安全

對 terminal plugin 宣告 optional 相依並附帶設定檔。但 optional 相依只保證本 plugin 仍能載入，不保證 adapter 裡的型別解析得開——terminal plugin 被停用時觸碰那些型別會在執行期失敗。

因此面板層在觸碰 adapter 之前，先確認 terminal plugin 的類別在本 plugin 的類別載入器下解析得開。這個檢查本身不觸碰任何 terminal 型別；JVM 的延遲載入保證檢查未通過時 adapter 的類別根本不會被解析。檢查失敗即等同「沒有可送出的目標」，走剪貼簿。

**實測修正**：檢查一度改用平台的 plugin 查詢 API，兩個候選都不可用——以識別碼查描述元再讀啟用狀態的那個已標為 deprecated，改讀已載入清單的那個標為 `@ApiStatus.Internal`，後者會讓 Plugin Verifier 直接判定失敗。最後改為直接詢問類別能否解析，理由不只是繞開標註：optional 相依本來就只在該 plugin 運行時才把它的類別放進可及範圍，所以「解析得開」正是這裡真正要問的那件事，而「已安裝」「已啟用」都只是它的鄰近命題。結果快取，因為它不重啟 IDE 就不會變。

### 多選時停用整個子選單

子選單的可用性以「選取中恰好有一個 change 節點」為條件。既有的複製動作允許多選並以換行串接，那個語意套到指令上會變成多行連續指令，對接收端幾乎必然是錯的。群組節點與 artifact 節點與既有複製行為一致地被忽略，不阻擋判斷。

## Implementation Contract

**行為**

- 在樹的右鍵選單中，既有的 Copy Change Name 之下出現一個子選單。選取中恰好有一個 change 節點時可用，否則整個子選單停用。
- 子選單包含四個項目，順序固定：apply、ingest、archive、commit。每個項目的文字是該指令套用選中 change 名稱後的完整結果，例如選中名為 `add-search` 的 change 時，第一項顯示 `/spectra-apply add-search`。
- 子選單標題在有可送出目標時為 `Send to Terminal`，否則為 `Copy Command`。
- 「有可送出目標」的定義：terminal plugin 已安裝且啟用、Terminal 工具視窗中有一個被選中的 tab、且該 tab 的終端連線已就緒。三者任一不成立即為沒有目標。
- 有目標時觸發項目：該行指令文字被寫入目標終端機的輸入位置，不附加換行也不觸發執行；Terminal 工具視窗被啟動，焦點移到該 tab。剪貼簿內容不變。
- 沒有目標時觸發項目：同一行指令文字被寫入系統剪貼簿。焦點不移動，不顯示通知。
- 兩種路徑都不觸發檔案系統掃描，樹的展開狀態、排序與過濾字串維持不變。

**介面與資料形狀**

- 指令種類以列舉表示，四個成員各自持有其 slash 指令名稱。
- 指令文字產生是純函式，輸入為指令種類與 change 名稱，輸出為單行字串，格式為 slash 指令名稱、一個半形空格、change 名稱，結尾無換行。
- 「取得目前可送出的目標」與「把文字送到目標」由同一個 adapter 物件提供，該物件是全 plugin 唯一 import terminal 型別的地方。
- 面板層取得 adapter 之前先做 plugin 啟用檢查，該檢查只用平台 API。

**失敗模式**

- terminal plugin 未安裝或被停用：等同沒有目標，靜默走剪貼簿。不記錄警告，這是預期狀態而非錯誤。
- 有選中的 tab 但終端連線尚未就緒：等同沒有目標，走剪貼簿。
- 寫入終端機時拋出例外：記錄到 IDE log，並改走剪貼簿，使用者仍拿得到指令文字。不彈出對話框。
- 選取中沒有 change 節點或有多個：子選單停用，不做任何事。

**驗收條件**

- 純函式層以既有的 JUnit 測試覆蓋：四個指令種類各自對一個 change 名稱產出預期的單行字串；多選與非 change 節點的選取判定回傳「不可用」。這些測試不得引入平台測試框架。
- 建置後在真實 IDE 中手動驗證三件事：目標 tab 裡出現指令文字且游標停在其後、Terminal 工具視窗取得焦點、按 Enter 後該指令才被送出。
- 手動驗證降級：關閉 Terminal 工具視窗後開啟右鍵選單，確認標題為 Copy Command，觸發後剪貼簿取得指令文字且無通知。
- 手動驗證載入安全：停用 terminal plugin 後重啟 IDE，確認 Spectra 工具視窗仍正常運作、子選單顯示 Copy Command 且可用。

**範圍界線**

- 在範圍內：右鍵子選單、四個指令、送入選中 tab、焦點轉移、剪貼簿降級、標題切換、多選停用、optional 相依宣告、純函式測試。
- 在範圍外：自動執行指令、自動開 tab、偵測 Claude session、指令清單設定頁、依群組過濾、工具列按鈕、鍵盤快捷鍵綁定、既有 Copy Change Name 的任何行為改動。

## Risks / Trade-offs

- 使用的 terminal 存取點不屬於平台的穩定 API：Plugin Verifier 對本次實作回報 13 處 `@ApiStatus.Experimental` 使用，全部集中在改版終端機的分頁管理器、檢視與送文字建構器上。判定結果為 Compatible，內部 API 使用為零。未來 IDE 版本仍可能調整這些介面 → 全部收斂在單一 adapter 檔案，且任何取得目標失敗都降級成剪貼簿而非拋錯；即使該 API 在未來版本失效，功能退化成複製，工具視窗不會壞。
- 初版對「介面方法存在即代表兩個引擎都可用」的假設在真實 IDE 中被推翻（見上方送出決策的實測修正）→ 已改為兩引擎各自的路徑；其中改版引擎那條是預設路徑，且已在沙箱 IDE 中實測送出、未執行、焦點轉移三項皆符合。
- 使用者可能在切錯 tab 的情況下觸發送出 → 不代按 Enter 已將代價壓到「多一行未送出的文字」；焦點轉移也讓使用者立刻看見文字落在哪裡。
- 四個指令寫死，使用者想要第五個時得等下一版 → 接受。目前 plugin 完全無狀態，為此引入第一個設定服務與設定頁的成本遠高於加一個列舉成員。
- 子選單讓右鍵選單從一項變成兩項，複製 change 名稱的路徑多了一個鄰居 → 既有項目維持在第一位且行為不變，快捷鍵仍直接對應它。
